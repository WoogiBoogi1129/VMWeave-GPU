Flyt NW diagnostic variation: launch-loop/other-host residual spans 0.117726–0.235597 seconds. The largest observed variation is in this residual, while transfer/initialization/barrier timings are steadier. This does not isolate RPC, OS scheduling, or server-side contributions, or establish the cause of all between-round variation.
Interpretation: the fresh-process ranking is dominated by different allocation/initialization costs. Passthrough allocation/init is about1.6s, VMWeave about0.66–0.67s, and the reused Flyt backend incurs only milliseconds in application allocation plus about0.05s pre-main startup. This is not evidence that remoting accelerates GPU kernels. The post-allocation diagnostic has much larger remoting overhead.
Context lifecycle source evidence: Flyt returns an existing virtual server for the VM; VMWeave spawns a fresh session worker and opens its CUDA context. MPS is present for Flyt SM-affinity. Their individual causal effects are not isolated by this experiment.

Conditions: same physical GPU GPU-772181af-05a4-0c24-de59-8487bd37c142, driver580.173.02, CUDA12.8.93; same measured binaries; VM8vCPU16GiB; QEMU CPUs32–39, remoting backend CPUs40–43; remoting allocations100%/8192MiB.
Flyt requires an MPS backend for its SM-affinity path. VMWeave uses its published v0.5.3 worker path. This is a comparison of the deployed execution paths, including different initialization/context lifecycles.
Flyt data transport is SHM; control RPC remains. Both remoting backends run within the standard HAMi allocation environment.
Flyt source: pinned development branches, recorded cuDNN9 build-compatibility exclusion, available Host libtirpc commit used for Guest, and ipc-rs ftok CString fix. NW/LU do not exercise cuDNN. This baseline is qualified for these two workloads, not all CUDA applications.
Three samples cannot establish small statistically significant differences; no universal performance or training-throughput claim.
