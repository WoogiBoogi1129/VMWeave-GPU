# Flyt MPS GPU 공유 성능 간섭 검증 및 VMWeave 비교 계획

작성: 2026-10-26 KST. 상태: 사용자 검토용. 신규 실험·환경 변경 미실행.

## 1. 목적과 비교 범위

단일 물리 GPU에서 Flyt의 MPS 기반 공유 경로를 이용하는 두 VM에 대해, 상대 VM 부하가 관측 VM의 처리량에 미치는 영향을 측정한다. 이전 VMWeave 성능 경합 P의 워크로드와 처리량 산식을 유지하되 웜업을 생략하고 반복 수를 줄여 두 시스템의 성능 감소율 차이를 분석한다. 기존의 원인 규명 계획은 이번 실행 대상에서 제외한다.

주 질문은 다음과 같다.

1. Flyt에서 상대 VM의 메모리/연산 부하로 관측 MLP의 처리량이 얼마나 변하는가?
2. 기존 VMWeave와 신규 Flyt의 단독 대비 감소율은 얼마나 다른가?
3. 이 차이가 부하 규모와 관측 방향을 바꾸어도 유지되는가?

VMWeave는 재측정하지 않고 기존 원 P/확대 P 자료만 사용한다. 신규 실행은 Flyt에 한정한다. p99 및 기타 지연 백분위수와 그 변화율은 측정·집계·비교 대상에서 제외한다. 정확성 검증과 40초 요청 timeout은 유효한 처리량 측정을 위한 실행 점검으로 유지한다.

이는 서로 다른 시점에 측정된 두 공유 시스템의 처리량 감소율 비교다. Flyt와 VMWeave는 전송 경로, 백엔드 및 제한 구현도 다르므로 차이를 MPS 하나의 효과로 귀속하지 않는다. GPU 데이터 접근 격리, 장애 전파, 학습 성능 및 모든 워크로드의 무간섭은 이번 검증 범위에 포함하지 않는다.

## 2. 확인된 기존 근거

- [기존 VMWeave 보고서](../report.md): 원 P 및 확대 P 각각 새 VM 쌍 10회(방향별 5회), 3조건, 조건당 1260초. 정상 완료 각각 381,945건/381,011건. 평균 처리량 감소는 원 P 메모리 0.352%, 연산 0.315%; 확대 P 메모리 0.291%, 연산 0.369%다. 기존 보고서는 통계적 유의성을 확정하지 않았다.
- [기존 MLP](../probes/mlp.py): 기존 코드는 요청 지연 필드도 기록하지만 이번 분석에서는 사용하지 않는다. 측정 루프의 호출·동기화·검증·출력 동작은 유지하여 로그 변경에 따른 비용 차이를 줄인다. 원시 로그에 기존 지연 필드가 남더라도 p99 등으로 집계하지 않는다. 처리량에는 D2H 결과 전송, CPU 정확성 비교 및 요청별 JSON 출력도 포함된다.
- Flyt Rodinia 실행 기록: `../../ai-passthrough/results/20261026-rodinia-steady/reproduction/start-stack.py`, `server-pod.py`, `prepare.py`. MPS 데몬 및 Flyt SHM 경로를 사용하지만 단일 VM, compute_units=188, 메모리 8192MiB, 외부 Pod GPU 연산 설정 100%, SHM 4GiB 구성이다. 이번 2 VM/각 50%/2GiB 조건으로 검증된 구성이 아니다.
- 기존 Flyt Rodinia 성공은 해당 CUDA 워크로드의 실행 근거이며, 이전 MLP의 PyTorch 실행 호환성이나 두 VM 동시 동작의 검증 근거는 아니다.

## 3. 실험 조건 고정

| 항목 | 기존 VMWeave 조건에 맞출 Flyt 기준 및 확인 사항 |
|---|---|
| 물리 자원 | 동일 GPU UUID와 호스트, 동일 드라이버. 대상은 기존 RTX PRO 6000 Blackwell Server Edition. 당시 드라이버 580.173.02와 현 상태 차이를 기록 |
| VM | VM별 8 vCPU, 16GiB RAM, 동일 OS·Python·PyTorch·CUDA 사용자 라이브러리와 입력/가중치 해시 |
| 관측 작업 | FP32 eager MLP 1024→2048→1024, batch 32, seed 20261012, CPU thread 1, TF32 비활성화, 기존 결정론 설정 |
| 검증 | CPU FP32 기준, 모든 관측 출력 rtol=1e-4/atol=1e-6 비교. CPU fallback 금지 |
| GPU 자원 목표 | VM별 연산 설정 50%, VRAM 2048MiB. 단독 기준에서도 같은 설정 유지 |
| 세션 | VM별 독립 클라이언트와 백엔드 세션, Flyt는 VM별 virtual server/컨텍스트 대응을 확인. 양쪽 VM과 백엔드가 준비된 상태에서 측정 |
| CPU 배치 | 기존 기록에 따라 VM 및 백엔드의 총 CPU 예산·NUMA 정책·CPU 집합을 맞추고, 과거 기록이 없는 항목은 동등성 미확인으로 표시. Flyt MPS/관리 프로세스도 예산과 사용량에 포함 |
| 웜업 | 관측 MLP의 사전 50회 실행과 상대 부하의 사전 반복 실행 모두 생략. 별도 안정화 대기 없음 |
| 측정 | 조건당 목표 120초, 완료 건수 목표 없이 실제 정상 완료 수 사용, 요청 timeout 40초. VM/프로세스 시작·모델 및 버퍼 준비는 제외하되, 첫 요청부터 측정하고 초기 느린 표본도 포함 |
| 부하·방향 | baseline/memory/compute, A 관측·B 부하 및 B 관측·A 부하 |

SHM 용량은 기존 VMWeave 64MiB를 우선 목표로 하되 Flyt의 동일 용량 지원 여부를 확인한다. 프로토콜상 불가능하면 실제 용량과 차이를 명시하고 비교 조건을 수정한다. 근거 없이 같은 구성이라고 표기하지 않는다.

### 연산 50%와 메모리 한도의 비교 가능성

Flyt의 compute_units/SM affinity와 MPS 설정, VMWeave의 제한 구현은 동일 의미라고 가정하지 않는다. 다음을 사전 검사한다.

- 실제 SM 수, 요청/적용 affinity, MPS 서버 및 두 클라이언트 연결, VM→virtual server→GPU 컨텍스트 대응을 기록한다. GPU 이름과 설정 파일만으로 MPS 적용을 판정하지 않는다.
- 동일 GPU를 두 VM이 동시에 사용하며 상대 경로가 Native fallback 또는 다른 GPU로 우회하지 않는지 확인한다.
- 50% 요청의 반올림·지원 제약, 실제 적용 여부와 확인 수단을 명시한다. 물리 SM 독점 분할을 주장하지 않는다.
- VRAM 제한은 Flyt 측 회계/강제 계층과 두 클라이언트별 적용 여부를 확인한다. 공유 Pod의 합산 한도를 VM별 2GiB 강제 한도로 오인하지 않는다.
- HAMi 등 외부 제한이 MPS 전체에 적용되는지, 클라이언트별 제한과 중첩되는지 확인한다. 기본 정책과 적용 차이를 manifest에 남긴다.

동등한 설정을 구현할 수 없으면 본실험을 시작하지 않고 차이와 대안을 검토한다. 대안은 Flyt에서 구현 가능한 설정으로 측정하고 조건 차이를 명시하는 것이다. VMWeave 재측정은 대안에 포함하지 않으며, 차이가 남으면 기존 P의 동일 조건 재현으로 부르지 않는다.

## 4. 부하 행렬

| 캠페인 | baseline | memory | compute |
|---|---|---|---|
| 원 P 부하 조건 | 상대 VM 준비 후 유휴 | 상대 VM 자기 128MiB FP32 버퍼 반복 곱셈, 매 연산 동기화 | 상대 VM 1024×1024 FP32 행렬 곱, 매 연산 동기화 |
| 확대 P 부하 조건 | 상대 VM 준비 후 유휴 | 상대 VM 자기 1024MiB 버퍼 반복 연산, 128회 제출마다 동기화 | 상대 VM 8192×8192 FP32 행렬 곱, 128회 제출마다 동기화 |

부하 완료량과 실제 관측 구간 중첩을 수집한다. memory라는 이름만으로 DRAM 대역폭 포화를 주장하지 않는다. 관측 MLP만 결과 정확성을 검증하는 기존 범위도 유지한다.

같은 부하 프로그램도 시스템별 실행 속도가 달라 실제 GPU 부하량이 달라질 수 있다. 주 실험은 기존 방식과 같은 최대 속도 제출 조건으로 수행하고, 부하 완료량/초와 GPU 활동을 함께 보고한다. 실제 부하량 차이가 크면 그 차이를 비교 해석의 제한으로 보고한다. 기존 자료에 부하 완료량이 없으면 미확인으로 남긴다. 양 시스템의 제출률을 새로 맞추는 추가 대조 실험은 수행하지 않는다.

## 5. 진행 단계와 통과 기준

### 1단계 — 준비 및 비교 조건 확정

기존 원/확대 실행기와 manifest에서 부하와 조건 전환 규칙을 추출한다. 실험용 실행기에서 관측/부하 웜업 루프를 제거하고 제품 코드는 변경하지 않는다. 필수 초기화와 실제 부하 시작을 웜업으로 대체하지 않는다. Flyt 소스 커밋, 빌드 수정, 이미지 digest, Guest/Host 라이브러리 해시, MPS 설정을 고정한다. VMWeave는 기존 시험 소스 `01b7e2a01fafaaaadbc43c5913bcbd8eca5458e5`의 보존 자료를 읽고 재집계하는 데 한정하며, 이미지 복구·배포·재실행은 하지 않는다.

기존 VMWeave `evidence/20261013/per-run.csv`와 `evidence/20261014-supplement/per-run.csv`, summary 및 원시 자료의 해시를 고정하고 처리량 감소율을 검산한다. 필요한 원본이 없으면 해당 분석의 한계를 표시한다. 기존 결과·제품 파일은 덮어쓰지 않는다.

통과 조건: 기존 VMWeave 기록과 Flyt의 워크로드 및 자원 설정 대응표 확정, Flyt 독립 VM 2개 실행 경로 확인, 동등하지 않은 조건의 해소 또는 검토 완료.

### 2단계 — 실행 전 정적 점검 및 첫 측정의 기능 확인

- 별도의 180초 파일럿은 생략한다. 라이브러리 의존성·설정·MPS 연결을 사전 점검하고 실제 MLP 정확성과 부하 완료는 첫 정식 측정부터 확인한다. 기존 PyTorch 번들의 ABI/API 호환성도 첫 실행 결과로 검증한다. 필요 시 어댑터는 실행 경로 설정에 한정하고 수학 연산·입력·측정 경계를 유지한다.
- 모델이나 연산 구현을 바꿔야 실행되는 경우 본실험을 보류한다. 기존 VMWeave와 동일 워크로드 비교가 불가능한 이유와 수정 범위를 검토받으며, VMWeave 재실행으로 해결하지 않는다.
- 첫 반복도 동일한 측정 규칙으로 진행하며 정상 완료하면 5회에 포함한다. 첫 반복 뒤 재워밍업이나 초기 표본 제거를 하지 않는다. 기능 실패는 실패 기록으로 남기고 진행을 중단한다.
- 모든 관측 결과 일치, 오류/타임아웃 없음, 두 부하의 실제 완료 및 구간 중첩, MPS 클라이언트 연결, 메모리/연산 설정 적용을 확인한다.
- 두 VM 중 하나가 종료하면 공유 MPS 백엔드가 다른 VM에 미치는 영향을 측정 구간에 섞지 않도록 두 관측 종료 후 정리한다.

진행 조건: 사전 정적 점검 후 첫 정식 반복에서 3조건의 정확성과 실행 경로를 확인한다. 실패하면 원본을 보존하고 남은 반복을 중단한다. 이 단계는 추가 측정 구간을 만들지 않는다.

### 3단계 — 본실험

본실험 구성은 **Flyt 1시스템 × 2캠페인 × 5개 독립 VM 쌍 × 3조건 = 30구간**이다. 여기서 5회는 방향별 5회가 아니라 캠페인당 총 5회이며, 한 반복에서 baseline/memory/compute를 각각 한 번 측정한다. 원 P 조건은 A 관측 3회/B 관측 2회, 확대 P 조건은 A 관측 2회/B 관측 3회로 배정한다. 두 캠페인의 표본은 합산하지 않는다. 각 반복에 새 VM 쌍과 독립 세션을 사용한다. VMWeave 신규 실행 구간은 0개다.

- Flyt의 각 반복에서 3조건 순서를 고정 seed로 무작위화하고 가능한 범위에서 위치를 균형화한다. 웜업이 없어 첫 조건이 초기 실행 비용의 영향을 더 받을 수 있으므로 실행 순서를 결과에 병기한다. 이전 부하의 작업 배출과 자원 회수 후 다음 조건을 시작한다.
- Flyt baseline은 항상 해당 캠페인·해당 반복에서 얻는다. VMWeave는 기존 각 반복의 baseline을 사용한다. 과거 VMWeave baseline으로 Flyt 처리량을 정규화하지 않는다.
- 측정 기간은 조건당 목표 120초로 고정하고 기존 10,000건 목표는 삭제한다. 첫 요청 직전에 시계를 시작하고 120초가 지나면 새 요청 제출을 중단한다. 이미 시작한 요청은 완료 또는 기존 40초 timeout까지 기다리고 그 시간을 실제 경과 시간에 포함한다. 완료 수/실제 경과 시간으로 처리량을 구하며 정확히 120초였다고 표기하지 않는다. 오류/timeout이 발생한 구간은 유효한 정상 처리량 비교에서 구분하고 실패 사실을 보고한다.
- 로깅은 기존과 같은 경계를 유지하고 무거운 GPU/API 프로파일링은 본 측정에서 제외한다. Flyt telemetry 설정을 고정하고 기존 VMWeave와 수집 항목·주기의 차이를 기록한다.
- 실패·중단·재실행 조건을 protocol에 사전 등록한다. 실행 오류나 결과 불일치를 단순 이상치로 제외하여 성공 결과만 비교하지 않는다.

본실험은 캠페인당 5회로 고정하며 검출력 확보를 이유로 자동 증설하지 않는다. 120초 × 5회로는 약 0.3%의 작은 차이를 구분하기에 부족할 수 있다. 이번 목적은 단시간 조건의 탐색적 처리량 감소율 비교이며, 기존 작은 차이의 정밀 재현은 보장하지 않는다. 실패로 유효 반복 수가 줄면 그대로 보고하고, 추가 반복이 필요하면 별도로 검토받는다.

웜업을 생략하므로 초기 커널/라이브러리의 지연 초기화, 캐시 및 클럭 상태 변화가 측정에 포함될 수 있다. 모델/입력 준비 이후 첫 요청 직전에 처리량 시계를 시작하며 초기 요청을 제외하지 않는다. 상대 부하는 버퍼 준비 후 실제 부하 루프를 시작하고 관측과의 시작 시각 차이를 기록한다. 별도 예열 루프나 안정화 대기는 두지 않는다. 기존 VMWeave는 웜업을 수행했으므로 이번 결과를 동일한 정상 상태 조건의 재현으로 표현하지 않는다.

### 4단계 — 분석 및 검토 보고

시스템 s, 반복 r, 부하 c에 대해:

- 처리량 Q = 정상 완료 수 / 관측 경과 시간.
- 처리량 감소율 D(s,r,c) = 100 × [1 − Q(s,r,c)/Q(s,r,baseline)]. 음수는 처리량 증가로 그대로 표시한다.
- 주 결과는 기존 방식과 같이 반복별 D의 동일 가중 평균이다. Flyt의 방향별 표본 수가 3/2로 불균형하므로 방향별 결과와 두 방향 평균을 50:50으로 가중한 보조 결과도 표시한다. 기존 VMWeave 10회를 임의로 5회만 골라 비교하지 않는다.
- 주 비교 ΔD = 평균 D(신규 Flyt) − 평균 D(기존 VMWeave), 단위 percentage point(%p). 양수면 이번 Flyt 캠페인에서 관측된 상대 감소가 더 크다. 서로 다른 시점의 반복을 짝짓지 않는다.

절대 처리량은 감소율 산출 근거와 해석 맥락으로 함께 제시한다. 낮은 단독 성능 때문에 감소율만 작아 보이는 경우를 구분하고, 간섭률만으로 어느 시스템이 더 빠르다고 쓰지 않는다. 부하 VM 완료량/초와 GPU 활동은 부하 유효성 점검 자료로 사용한다. 지연시간과 백분위수 비교표·그래프는 작성하지 않는다.

독립 표본은 요청 수가 아닌 VM 쌍 반복이다. 5개 반복의 감소율 전체, 평균·표본 표준편차·최솟값/최댓값을 보고한다. 방향별 2~3회에 불과하므로 bootstrap 신뢰구간 및 유의성 검정은 이번 축소 실험의 분석 대상에서 제외한다.

시스템 간 비교는 기술적 비교로 제한한다. ΔD는 측정 시점·환경·버전·실제 부하량뿐 아니라 웜업 유무, 1260초와 120초의 관측 길이 및 방향별 구성 차이도 포함한다. ΔD의 부호만으로 시스템 우열이나 MPS의 인과 효과를 확정하지 않으며, 작은 차이나 차이 미관측을 동등성·무간섭으로 해석하지 않는다.

최종 비교표는 원/확대 × memory/compute의 4행으로 구성하고, 기존 VMWeave 평균 감소율, 신규 Flyt 평균 감소율, ΔD(%p), 방향별 결과와 비교 조건의 차이를 제시한다. 과거와 신규 요청을 합치거나 기존 VMWeave 결과를 신규 측정으로 표기하지 않는다.

## 6. 측정 시간 축소 검토 및 실행 예산

조건당 60/120/180초를 비교하여 **120초를 기본안**으로 선택한다. p99를 분석하지 않고 10,000건 목표도 삭제하므로 기존 1260초를 유지할 필요는 없다. 다만 짧은 구간에서는 웜업 없이 포함되는 초기 비용과 시간 변동의 상대적 영향이 커진다.

| 조건당 목표 시간 | 30구간 순수 목표 시간 | 기존 약 10건/초를 가정한 구간당 완료 수 | 검토 |
|---|---:|---:|---|
| 60초 | 30분 | 약 600건 | 초기 비용·일시적 변동의 영향이 커 기본안에서 제외 |
| 120초 — 채택 | 60분 | 약 1,200건 | 실행 비용을 줄이면서 60초보다 관측 시간을 확보하는 탐색적 절충안 |
| 180초 | 90분 | 약 1,800건 | 관측은 늘지만 정밀도 개선을 사전 보장할 수 없어 기본안에서 제외 |

위 완료 수는 과거 VMWeave 처리량으로 계산한 규모 예시이며 Flyt 성능 예측이나 최소 통과 기준이 아니다. 약 10건/초에서 0.3% 차이는 120초 동안 약 3.6건 차이에 해당한다. 이는 검출력 계산이 아니며 요청 자기상관·시작 비용·반복 간 변동 때문에 작은 차이의 판정은 특히 제한된다. 정상 요청이 없으면 감소율을 계산하지 않고 실행 실패/측정 불가로 보고한다.

모든 반복에 같은 120초 규칙을 적용하며 관측 결과에 따라 유리한 구간만 늘리거나 골라내지 않는다. 원시 요청 시각으로 가능하면 앞/뒤 60초의 완료 수를 점검하여 시간 추세를 보조 자료로 남기되, 첫 60초를 웜업으로 버리거나 주 지표를 후반부로 교체하지 않는다. 이 두 부분을 독립 반복으로 세지 않는다. 짧은 실행에서 판단이 불가능하면 그대로 보고하며 추가 측정은 자동 수행하지 않는다.

기존 VMWeave는 1260초 전체 결과를 주 비교값으로 유지한다. 기존 원시 로그에 요청 완료 시각과 필요한 경계 정보가 모두 있으면 첫 120초 처리량을 보조 재집계할 수 있으나, start/latency 필드가 결과 검증·로그 출력을 포함한 완료 시각을 제공하는지 먼저 확인한다. 경계를 정확히 복원할 수 없으면 단시간 비교를 생략한다. 유리한 120초 구간을 선택하거나 잘라낸 구간을 독립 반복으로 늘리지 않는다. 보조 재집계도 과거 웜업의 영향을 제거하지 못하며 VMWeave 신규 실행은 하지 않는다.


| 범위 | 구간 수 | 순수 관측 시간 |
|---|---:|---:|
| Flyt 원 P 조건, 5쌍 × 3조건 × 120초 | 15 | 30분 |
| Flyt 확대 P 조건, 5쌍 × 3조건 × 120초 | 15 | 30분 |
| 본실험 합계 | 30 | 60분 |
| 별도 파일럿·웜업 | 0 | 0시간 |
| VMWeave 신규 실행 | 0 | 0시간 |

순수 목표 관측 시간은 60분으로, 직전 계획의 10.5시간 대비 약 90.5% 감소한다. 종료 시 진행 중인 요청의 완료 대기, VM 생성·필수 초기화·설정·복구는 별도다. 60분은 전체 작업 완료 예상 시간이 아니며 실제 경과 시간을 기록한다.

새 캠페인 디렉터리에 아래 자료를 저장한다.

- protocol/manifest: 소스·이미지·라이브러리 해시, GPU UUID, 자원 설정과 실제 적용 증거, 무작위 순서, 제외 규칙.
- 원시 요청 로그, 정확성 결과, 부하 완료량, MPS 연결·VM별 매핑, CPU/GPU telemetry, 실패 기록과 SHA256.
- 반복별 CSV 및 독립 재집계 코드, 절대 처리량/처리량 감소율/ΔD 그래프, 방향별 분석, 비교 가능성 및 제한 사항.
- 최종 보고서와 cleanup 기록. 기존 P 결과는 수정하거나 합산하지 않는다.

완료 범위는 측정에서 끝나지 않고 **기존 자료 재집계 → 신규 Flyt 집계 → 비교 보고서·그래프 생성 → 검증 → 원격 저장소 main 반영**까지다. 아래 파일명은 계획이며 실제 결과를 얻기 전에 수치·그래프·완료 판정을 작성하지 않는다.

저장소의 기존 관례에 따라 전체 로컬 원본은 `experiments/thesis-isolation/results/<실행일>-flyt-mps-comparison/`, 공개할 선별 증거와 보고서는 `experiments/thesis-isolation/evidence/<실행일>-flyt-mps-comparison/`에 둔다. 실행일과 고유 실행 ID를 manifest에 기록한다.

| 산출물 | 내용 |

필수 그래프는 다음 세 종류다. Python의 표준 plotting 도구로 CSV/JSON에서 생성하며 수치를 이미지 편집으로 수정하지 않는다.

1. **처리량 감소율 비교:** 원 P/확대 P를 패널로 나누고 memory/compute별 Flyt·VMWeave 평균과 개별 반복 점을 표시한다. 오차 막대가 있으면 표본 표준편차임을 명시한다. y축은 감소율(%), 0 기준선을 표시하고 음수도 보존한다.
2. **감소율 차이:** 네 조건의 ΔD = Flyt − VMWeave를 %p 단위로 표시한다. 양수/음수의 의미를 범례에 적고 인과적 우열 표시나 유의성 별표는 사용하지 않는다. 차이를 상대 퍼센트로 오표기하지 않는다.
3. **방향별 감소율:** A 관측/B 관측을 구분하여 반복 점과 평균, 각 표본 수를 표시한다. 3/2 반복 구성 및 방향별 변동이 전체 평균에 가려지지 않도록 한다.

절대 처리량은 보고서의 baseline/동시 부하 표로 제공하여 감소율 산출을 검산할 수 있게 한다. p99와 기타 지연 지표는 산출물에 추가하지 않는다. 모든 비교 그래프에 **Flyt: 120초·웜업 없음·캠페인당 n=5 / VMWeave: 기존 1260초·웜업 있음·n=10**을 캡션으로 명시하고 실제 유효 표본 수가 다르면 함께 표시한다. 시스템별 색상은 모든 그림에서 고정하고 3D 효과나 차이를 과장하는 축 절단은 사용하지 않는다.

보고서 결론은 ‘해당 조건에서 관측된 감소율과 그 차이’를 기술한다. 작은 차이를 확인하지 못한 경우도 그대로 보고하며 성공적인 차이를 얻는 것을 완료 조건으로 삼지 않는다. 실패/호환성 문제로 비교가 불가능하면 해당 칸을 N/A와 사유로 표시하고, 없는 수치를 0으로 채우지 않는다.

## 8. 산출물 검증 및 main 저장소 반영

반영 대상은 현재 origin인 `WoogiBoogi1129/VMWeave-GPU`의 **원격 main 브랜치**다. 이번 요청 단계에서는 계획서만 수정한다. 계획 승인 후 실행 범위에 결과 생성과 main 반영까지 포함한다.

1. **재현 가능한 집계:** `experiments/thesis-isolation/runner/`에 신규 집계·그래프·보고서 생성 도구를 추가한다. 하나의 문서화된 명령으로 공개 증거에서 CSV/JSON과 보고서/그래프를 재생성할 수 있게 하며, 이 명령은 GPU 실행이나 클러스터 변경을 하지 않는다. 필요한 plotting 의존성과 버전을 기록한다.
2. **수치 검증:** 정상 완료 수/실측 경과 시간, 반복 내 baseline 대응, 평균의 가중 방식, ΔD 부호·%/%p 단위, 기존 VMWeave 집계와의 일치를 확인한다. 원/확대·방향·조건 누락과 실패를 점검하며, 평균 처리량의 비율을 반복별 감소율 평균으로 잘못 대체하지 않는다.
3. **문서·그림 검증:** 같은 comparison 데이터를 사용해 표·본문·그림 수치를 대조한다. PNG/SVG/PDF 및 HTML을 실제 렌더링하여 글꼴·한글·축·범례·캡션·잘림을 확인하고 링크와 이미지 경로를 검사한다. 보고서의 모든 완료 주장은 원시 증거로 연결한다.
4. **공개 자료 선별:** 재집계에 필요한 요청/조건 기록과 해시는 공개하되 키·토큰·자격증명·비공개 관리 로그·대형 이미지/바이너리는 커밋하지 않는다. 선별 과정과 제외 파일의 종류를 기록한다. 로컬 전체 원본은 보존한다.
5. **저장소 문서 연결:** `experiments/thesis-isolation/README.md`에 새 보고서·그래프·재현 명령 링크와 실제 완료 범위를 추가한다. 기존 `report.md`와 과거 증거 수치는 보존하고 필요하면 신규 비교 보고서 링크만 추가한다.
6. **변경 분리 및 반영:** 기존 작업 트리의 제품 코드와 타 실험 변경을 보존한다. 최신 origin/main을 기준으로 별도 작업 브랜치/격리 작업 공간에서 이번 계획·실행 도구·공개 결과·문서만 명시적으로 선택해 커밋한다. diff와 공개 대상 파일을 검토한 후 저장소 정책에 맞게 main에 병합·push한다. 보호 브랜치라면 PR과 필수 검사를 거쳐 병합하며 강제 push로 우회하지 않는다.
7. **원격 확인:** origin/main의 커밋 SHA와 변경 파일을 다시 확인하고, 보고서·그래프·증거 디렉터리의 원격 링크를 사용자에게 제공한다. main에 반영되지 않은 로컬 커밋이나 미병합 PR을 완료로 보고하지 않는다. 권한/필수 리뷰 등으로 반영이 막히면 완료된 산출물, PR/커밋, 남은 조건을 명시한다.

최종 완료 기준은 실제 수행 범위와 실패를 포함한 비교 보고서, 필수 그래프, 재집계 가능한 증거/코드, 검증 및 환경 복구 기록이 준비되고 **원격 main에 반영된 사실까지 확인**하는 것이다. 실험 결과가 유의하거나 Flyt가 우수해야 한다는 조건은 없다. 이 후처리·게시 시간은 순수 GPU 관측 60분에 포함되지 않는다.

## 9. 중단·복구 및 검토 요청

시험 전용 VM/채널/백엔드와 MPS 디렉터리를 사용한다. GPU와 프로세스 소유 관계를 확인하고 운영 VM/공유 데몬을 임의 종료하지 않는다. 결과 불일치, 예상 밖 GPU 오류, 운영 자원 영향, 경로/할당 불일치가 있으면 해당 실행을 중단하고 원본을 보존한다. 완료 후 시험 자원과 affinity/제한 설정을 원복하여 운영 상태를 대조한다.

검토 제안: **웜업과 별도 파일럿 없이, Flyt 원/확대 조건 각각 총 5회(조건당 목표 120초, 합계 30구간, 순수 목표 관측 60분)를 측정한다.** 첫 정식 반복에서 기능을 확인하며, 기존 VMWeave와는 웜업·반복 수·관측 길이가 다른 처리량 감소율의 기술적 비교로 보고한다. 이후 비교 분석 보고서·그래프·재현 자료를 생성하고 검증하여 원격 main 반영까지 완료한다. 현재 요청은 계획 검토이므로 GPU 실험·결과 생성·커밋·push는 수행하지 않았다. 계획 승인 시 이 전체 범위를 기준으로 진행하며, 동등 조건이 성립하지 않아 비교 질문이 달라지는 경우에만 수정안을 다시 제시한다.


## 실행 전 점검 — 2026-10-26

계획 실행 승인을 받아 읽기 전용 환경 확인 및 기존 CSV 재집계를 수행했다. GPU UUID와 드라이버 580.173.02는 기존 시험과 일치하고 점검 시 대상 GPU 메모리 사용은 0MiB였다. 기존 처리량 감소율 4개는 재집계와 일치했다. 상세 점검은 로컬 `.local/flyt-mps-comparison-20261026/preflight.json`에 보존했다. 아직 신규 GPU 측정·클러스터 변경·커밋·push는 하지 않았다.

**조건 차이 수정안 — 사용자 승인 완료:** 사용 가능한 Flyt 클라이언트 관리자 소스의 `vcuda_client_handler.rs:13`은 `PROC_SHM_SIZE = 2<<28`(512MiB)를 상수로 사용하고, 260~266행에서 프로세스별 할당과 offset 증가에 적용한다. 기존 VMWeave의 64MiB와 다르며 이 소스 경로에는 런타임 용량 설정이 없다. 64MiB backing만 제공하면 프로세스가 할당받은 범위보다 작으므로 그대로 실행하지 않는다.

제안은 제품 코드의 상수를 변경하지 않고 **Flyt 프로세스당 512MiB / 기존 VMWeave 64MiB**로 비교하는 것이다. 실제 backing 용량은 별도로 기록하고 두 VM의 backing을 분리한다. Flyt가 사용하는 고정 경로 `/dev/shm/ivshmem-0-ub11.dat`는 백엔드별 mount namespace로 구분 가능한지 준비 단계에서 확인한다. SHM 차이는 manifest·보고서·그래프 캡션에 명시한다. GPU VRAM 2GiB와 호스트 SHM 용량을 혼동하지 않는다.

사용자가 “설정 차이를 명시하고 진행”으로 승인했다. SHM 차이를 명시하여 자원 준비, 연산 제한·메모리 제한·PyTorch 호환성 점검 및 승인된 산출물/main 반영 작업을 진행한다.


## 실행 결과 — 초기화 실패로 본 측정 중단

SHM 차이 승인 후 두 시험 VM과 Flyt 백엔드 및 공유 MPS 데몬을 준비했다. 그러나 첫 MLP 프로세스는 PyTorch import 시 `cudaGetDriverEntryPointByVersion` 심볼 부재로 종료했다. 실제 CUDA runtime과 Flyt preload를 사용하는 설정 진단도 A 재사용 백엔드/B 새 백엔드에서 각각 40초 timeout으로 끝났다. 두 설정 진단은 성능 반복에 포함하지 않는다.

계획의 호환성 실패 중단 기준에 따라 **유효 측정 0/30구간**으로 종료하고 시험 자원을 회수했다. 기존 VMWeave는 재측정하지 않았다. 보고서와 그래프에는 과거 VMWeave 실측값을 제공하고 Flyt와 ΔD는 N/A로 표시한다. 결과와 제한은 [실행 보고서](../evidence/20261026-flyt-mps-comparison/REPORT.md)에 기록한다. 이 기록은 계획한 성능 비교를 달성했다는 의미가 아니다.
