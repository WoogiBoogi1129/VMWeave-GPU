## 3. I1 — 요청한 GPU·한도가 실제 실행 환경으로 연결되는가

**필요한 이유:** 9쪽의 Kubernetes 관리 계층은 CUDA 실행 성공 화면만으로 설명되지 않는다.
사용자의 GPU 요청을 실제 Worker 자원과 같은 노드의 VM 연결로 변환한 것이 자체 구현임을 보여준다.

**실행 구성**

1. 승인 profile과 VM 참조를 사용해 `count=1`, 메모리 `4096 MiB`, compute `50`, 세션 1개 요청을 만든다.
2. request/profile UID → Channel/allocation/generation → VM/VMI → Worker UID → host PID → GPU UUID를 수집한다.
3. VM과 Worker가 승인된 동일 노드에 있는지, Worker의 GPU UUID annotation·requests/limits가 요청과 일치하는지 확인한다.
4. 실제 실행 프로세스의 장치 접근과 HAMi-core 로드를 확인한다. Pod 설정만으로 실제 라이브러리 로드·GPU 사용을 추정하지 않는다.
5. 게스트 BAR2와 QEMU/Worker의 공유 backing 연결을 확인하고 I2 probe를 실행한다.

**반복:** I1+I2를 같은 VM 실행으로 묶어 독립 allocation 3회. 대규모 성능 표본이 아니라 배선·반복 동작 확인이다.
후속 시연은 녹화 없이 실제 터미널 정적 캡처와 원본 로그를 확보한다. I3의 실행에서도 같은 매핑 정보를 자동 수집한다.

**판정:** 요청→적용 memory/compute 일치, node·GPU UUID 일치, 독립 UID 연결, 실제 Ready·Mapped 및 GPU 실행 확인.
compute 값 일치는 **설정 전달 PASS**이고, 이용률 제한 PASS는 I4에서 판정한다.

**시각 자료 — 사용자 검토 후 수정:** [실제 터미널 절차 시연](results/2026-09-28-stage1-terminal/README.md)을 따른다.
자체 결과 UI를 만들지 않고 bash/kubectl/SSH/nvidia-smi의 실행 명령과 실제 출력을 표준 asciinema로 보존한다.
요청 등록 → VM·Worker 준비 → 요청/적용 비교 → Worker PID/GPU PID 대응 → 검산·회수를 단계별로 제시한다.
큰 UID는 화면에 읽기 쉬운 축약값을 표시하되 원본에는 전체 값을 남긴다.
**산출물:** `request.yaml`, `applied.json`, `placement.csv`, `binding.json`, 실제 터미널 기록·PNG·영상.

승인되지 않은 profile·범위 밖 한도 거절은 부록용 선택 검사다. 해당 상태 전이·거절 위치를 먼저 확인하고,
원래 구현이 admission 단계에서 즉시 거절한다고 가정하지 않는다.

## 4. I2 — 공유 메모리의 요청·응답이 실제 CUDA 실행으로 이어지는가

**실행 완료:** [2026-09-28 I2 결과](results/2026-09-28-stage2/README.md).
선택형 `FLYT_TRACE_REQUESTS=1`을 추가해 네 endpoint를 연결했다. 기존 PTX 정수 add 19 연산을
단일 1 MiB 버퍼의 전체 원소에 적용하는 probe로 구성했고 새 VM 3회에서 전수 검산을 통과했다.
아래는 설계 기준이며, 실제 입력·커널·로그·이미지·시각 자료는 연결한 결과 보고서가 기준이다.

**필요한 이유:** 10쪽은 `cudaMalloc`을 예로 든 구현 설명이다. CPU/GPU 이용률만으로 해당 중계 경로를 입증할 수 없다.

**프로그램과 흐름**

- 기존 GPU smoke의 검증된 PTX·입력·기준 결과를 유지한다. 별도 작은 요청으로 `cudaMalloc(1 MiB)` 예시를 표시한다.
- 할당 → H2D → 정수 커널 → synchronize → D2H → CPU 기준과 비교 → free를 실행한다.
- 복사한 전체 bytes와 정수 출력의 검사 개수·불일치 개수를 명시한다. 기준/입력 hash도 기록한다.
- guest submit, Worker take/dispatch, Worker respond, guest receive를 `allocation + generation + session_id + request_id`로 연결한다.
- 이미 있는 `FLYT_TRACE_CALLS`는 API·bytes·결과 수준이다. 양쪽의 동일 request ID 추적까지 필요하면 시연용 선택 로그를 보강해야 한다. 현재 화면에 그 정보가 이미 있다고 가정하지 않는다.
- trace에서 API 상태와 transport 상태를 분리한다. 응답 handle/Guest pointer/실제 GPU allocation의 의미를 구분하고 호스트 CPU 포인터 전달로 설명하지 않는다.

**판정:** 동일 요청의 송수신 대응, 실제 CUDA 성공, 정수 mismatch 0, free 성공.
요청별 시각은 각 시스템의 단조 시계를 기록한다. 동기화 오차를 무시하고 두 호스트 시각의 차이를 호출 지연으로 계산하지 않는다.
**시각 자료:** guest/Worker 로그를 나란히 보여주고 1 MiB 요청·같은 request ID·반환 성공을 강조한다.
이 화면은 구현 시연이며, trace를 켠 실행을 P1 성능 표본으로 사용하지 않는다.

기존 PyTorch 8조건·144 tensor 정확성 표는 응용 프로그램 실행 가능성을 보여주는 보조 자료로 재사용한다.
해당 버전의 FP32 eager MLP·SGD 범위임을 표시하고 PyTorch 전체 API·임의 모델 지원으로 일반화하지 않는다.
새 학습 검산 반복은 기본 계획에 넣지 않는다.

## 5. I3 — 두 VM의 동일 GPU 공유와 서로 다른 메모리 한도

**기존 자료 재사용:** 9/24 동일 GPU 공유 화면·영상, 1/4 GiB 각각의 할당/OOM/해제/재할당,
경계 suite 및 정상 회수 자료를 그대로 사용한다. 같은 기능을 모두 다시 반복하지 않는다.

**보완해야 할 주장:** 기존 단독 한도 시험 두 개를 나란히 놓는 것보다,
같은 GPU를 사용하는 A/B가 서로 다른 요청 한도로 동작하는 장면이 “VM별 자원 제공”을 직접 보여준다.

**신규 동시 시연 조건**

| 항목 | VM A / Worker A | VM B / Worker B |
|---|---|---|
| GPU | 동일한 물리 UUID 1개 | A와 같은 UUID |
| 메모리 한도 | 1024 MiB | 4096 MiB |
| 연산 설정 | 50 | 50 |
| 세션·공유 영역 | 1개·64 MiB | 1개·64 MiB |
| 큰 할당 요청 | 1536 MiB | 1536 MiB |
| 기대 결과 | 메모리 부족 반환 | 할당 성공 및 유지 |

설정 50은 이 실험의 통제 조건이며, 50% 연산 보장의 근거로 사용하지 않는다.
실행 전 context 예약량과 HAMi가 보고하는 여유량을 기록한다. B가 정상 조건에서 1536 MiB를 수용할 여유가 없으면
준비 조건 불충족으로 기록하고 원인을 먼저 해결한다. 성공하도록 본 측정 중 요청량을 바꾸지 않는다.

**순서**

1. A/B에서 서로 다른 입력의 작은 검산 커널을 실행해 각 경로를 확인한다.
2. B가 1536 MiB를 할당해 유지하고, 작은 검산 커널을 주기적으로 계속 실행한다.
3. A가 같은 1536 MiB를 요청하고 CUDA 메모리 부족 오류를 기록한다.
4. A가 여유량 안의 128 MiB를 요청해 성공·검산·해제를 확인한다. B의 기존 allocation과 실행은 유지한다.
5. B도 해제하고 양쪽의 정상 종료·회수를 확인한다. 단계별 10초 유지, 전체 약 60~90초의 로그·지표를 수집하고 정적 터미널·Grafana 화면으로 제시한다.

**반복:** 독립 pair 3회. 역할을 교환한 한도 시험은 선택 보완이며 기본 3회에 포함했다고 보고하지 않는다.
**판정:** A의 큰 요청만 예상 OOM, A의 작은 재요청 성공, B의 allocation 유지·진행·최종 검산 성공,
같은 GPU UUID와 서로 다른 Worker 확인, 양쪽 정상 회수.
이는 **메모리 한도 분리와 정상 OOM 후 동작**이며, 악성 커널·주소 침범 방지·장애 격리를 입증하는 실험이 아니다.

**시각 자료:** A/B 터미널의 동일 요청량과 서로 다른 결과, Grafana의 VM별 한도·HAMi 계상·앱 할당량,
B의 완료 카운터, 대상 GPU UUID. 장치 전체 메모리는 별도 패널로 둔다.
**산출물:** `allocation-events.csv`(VM/session, requested bytes, status, live allocated bytes, timestamp),
`validation.json`, `identity.json`, 원본 stdout/stderr·출력 표본, 터미널 정적 캡처, 단계 annotation이 있는 실제 Grafana 정적 화면. [완료 결과](results/2026-09-29-stage3/README.md)를 따른다.

**두 세션 합산 제한은 언제 추가하는가?**
9쪽의 “세션별 실행 프로세스”가 단순 구현 설명이면 기존 합산 제한 그림을 부록에 두면 충분하다.
“하나의 VM에서 여러 프로세스가 한도를 공동 사용하고 반환분을 서로 재사용한다”를 본문 기여로 주장할 때만,
Worker당 2세션에서 A 선행 할당 → B 초과 OOM → A 해제 → **같은 B 세션** 재요청 성공을 추가한다.
기존 `[성공, OOM]` 결과에는 마지막 교대 재사용 증거가 없다. VM 2대 시험으로 이를 대신하지 않는다.

## 6. I4 — 연산 설정값이 실제 제한으로 작동하는가

**최우선 점검 항목이다.** 기존 결과의 추가 그림 제작만으로 해결되지 않는다.
9/28 긴 커널은 설정 25/50/100에서 모두 약 52.4 kernels/s·92% 이용률이었고,
짧은 커널은 약 355 kernels/s·1% 이용률이었다. 이 자료는 보존하고 “제한 입증 전 관측”으로 사용한다.
특히 이미 1% 수준인 짧은 부하는 25%·50% 상한 시험의 충분한 입력 부하가 아니다.

### I4-A. 본 실험 전에 정책·계측을 진단

1. 설치 libvgpu의 해시·source commit·실제 mapping, 커널 실행 API와 interception 경로를 확인한다.
2. 현재 실행 프로세스의 연산 환경변수와 정책을 읽는다. 9/28의 기록은 정책 미지정(auto)였다.
   로컬에 확보한 b216ba1 소스는 `FORCE`/`DISABLE`과 공유 utilization switch를 구분한다.
   **auto가 실제로 어떤 상황에서 활성화되는지**까지 확인하며, 환경변수 문자열만으로 활성화를 추정하지 않는다.
3. 장치 전체 이용률, HAMi container 지표, 프로세스 이용률의 단위·실제 갱신 주기·PID 매핑을 확인한다.
   VM별 정책이라면 프로세스/Worker 단위 관측이 가능한지를 먼저 판단한다.
4. 기존 긴/짧은 커널 사이의 내부 반복 수를 최대 3조건으로 예비 탐색한다.
   제한이 비활성인 상태에서 충분히 포화되면서 반복 제출이 관측되는 부하를 선정한다.
   기준은 예비 계획에서 고정한다. 예: 60초 안정 구간 평균 장치 이용률 ≥80%, 출력 검산 정상.
   이 수치는 실험 부하 선택 기준이지 HAMi의 보장값이 아니다.
5. 선택한 동일 커널·한도·compute 25로 호스트+HAMi / VM+SHM+HAMi와 정책 강제 활성 / 비활성의
   2×2 진단을 각 1회 수행한다. 비활성 정책도 HAMi 메모리 제한·라이브러리가 남아 있는 조건임을 명시한다.
   실제 배포 버전이 해당 정책을 지원하는 것을 확인한 뒤 사용하며, auto 결과와 합산하지 않는다.

정책 변경이 필요하면 실험용 구성에서만 명시적으로 적용하고 새 버전/설정으로 기록한다.
호스트는 제한되는데 VM 경로는 제한되지 않는다면, Worker의 정책 전달·대상 PID·호출 interception을 우선 점검한다.
양쪽 모두 변화가 없거나 충분히 포화되지 않으면 반복 수를 늘리기 전에 계측·정책·부하 문제를 분리한다.
원인을 모르는 상태에서는 `NOT_EVALUATED` 또는 해당 계약에 대한 실패로 남긴다.

### I4-B. 진단이 성립할 때만 시간제 본 실험

- VM 1개, 메모리 4 GiB, 1세션, 같은 커널·입력·내부 반복 수·CPU 배치.
- 명시적으로 고정한 정책에서 compute 25/50/100 × 독립 3회 = **9회**.
- 준비 실행 최소 10초 및 50회 이후 90초 실행하고 중앙 60초를 비교 구간으로 사용한다.
  중앙 구간의 완료 카운터·단조 시각을 직접 기록한다. 초기/최종 표본을 선형 보간해 완료 수를 만들지 않는다.
- 실제 GPU 이용률 시계열, 완료 커널 수/초, limiter 대기 지표(실제로 관측 가능할 때), 출력 검산을 수집한다.
- 처리율도 **동일 60초 동안 완료한 작업 수**로 비교한다. 고정 N 커널의 완료시간 시험은 넣지 않는다.

**사전 판정 계약:** 제한 대상·정책·관측 지표·안정 구간·허용오차·유효 표본률을 본 측정 전에 문서화한다.
상한 정책이면 평균 이용률이 설정값과 정확히 같아야 한다고 판정하지 않는다.
예를 들어 허용 상한을 `설정값 + 10 percentage points`로 채택한다면 연구자가 정한 허용 기준임을 밝히고,
비활성 포화 대조군·실제 작업 완료·25/50/100의 처리율과 함께 평가한다. 이용률 0은 제한 성공으로 처리하지 않는다.
공식/구현 계약과 맞지 않는 기준이면 이 예시를 사용하지 않고 사전에 다시 정의한다.

**시각 자료:** 한 run만 선택한 Grafana에서 설정선·정책·이용률·처리율·실행 구간을 함께 표시한다.
녹화 없이 실제 터미널/Grafana 정적 캡처와 9회 처리율/이용률 비교 그림을 만든다. 단일 화면이 모든 반복의 증거를 대신하지 않는다.

**중단 기준:** 진단 2×2에서 활성 조건·측정 대상·포화 부하를 확인하지 못하면 I4-B를 자동 실행하지 않는다.
구현 수정 후 새 측정 묶음으로 다시 시작하거나, 발표를 “연산 설정 전달 및 관측된 한계”로 좁힌다.

## 7. I5 — 정상 회수와 재사용

기존 20회 정상 종료·회수·재사용 결과, 호스트 관측 회수 화면 및 최종 감사를 재사용한다.
정상 종료 뒤 Released, 해당 VMI/Worker 종료, 해당 allocation backing 회수, 해당 GPU 프로세스 종료를 구분한다.
현재 버전의 정상 회수는 I1~I4의 각 cleanup 기록으로 보완한다. 별도 20회 캠페인은 기본 계획에서 제외한다.
버전이 달라진 결과의 반복 횟수를 합치지 않는다. 기존 시작/회수 시간은 당시 관측값이며 서비스 SLO로 일반화하지 않는다.

## 8. 성능 분석 장: 직접 실행 기준과 이전 FLYT 대비 오버헤드

### P1. 호스트 직접 실행 대비 제안 경로의 처리율

고정 작업량 완료시간 없이도 **동일 작업 단위의 60초 처리율**로 경로의 실행 비용을 분석할 수 있다.
다만 직접 실행은 “호스트 컨테이너+HAMi”이고 passthrough VM이 아니다.

| 조건 | 고정 내용 |
|---|---|
| 경로 | 호스트+HAMi / VM+SHM+Worker+HAMi |
| 작업 | 같은 probe·PTX·입력·seed·검산·1회당 kernel 수와 동기화 방식 |
| 모드 | resident: 초기 입력 1회 후 kernel+sync 반복 / transfer: 매회 2 MiB H2D→kernel+sync→2 MiB D2H |
| 자원·정책 | 같은 물리 GPU, 4 GiB, compute 100, 양쪽 같은 명시적 연산 정책. 요청 100만으로 무제한이라고 가정하지 않음 |
| 측정 | 준비 실행 최소 10초 및 50회, 측정 60초, 조건별 독립 3회. 총 2경로×2모드×3회 = 12회 |
| 순서 | 반복별 경로 순서를 교차하고 사전 순서표 보존. 부팅·설치·최종 검산·회수는 성능 구간 밖 |
| 관측 | 동기화 완료 작업 수/실제 단조 시간, CPU 사용량, GPU 이용률, 최종 정확성 |

그래프는 반복별 점과 평균·표본 표준편차를 제시한다.
주 지표는 `처리율 유지율 = VM 처리율 / 직접 처리율`, `처리율 감소율 = (1 - 유지율) × 100`이다.
호스트 CPU polling·VM·Worker·복사·동기화가 포함된 **전체 경로 차이**이며 순수 SHM 통신 지연이라고 부르지 않는다.
단일 장시간 커널만으로 작은 호출의 비용을 일반화하지 않도록 resident/transfer를 함께 비교한다.

VM 8 vCPU와 Worker 4 CPU, 직접 실행 프로세스 CPU 집합, SMT·NUMA·계측용 CPU 배치를 실제 값으로 고정·공개한다.
양쪽의 총 CPU 비용은 같다고 가정하지 않고 따로 보고한다. guest/host 중첩 CPU 시간을 단순 합산하지 않는다.
다른 실험의 기존 60초 결과는 부하 선택에 참고하되, 정책·버전·배치가 다른 신규 baseline과 한 쌍으로 묶지 않는다.
I4가 미판정이어도 양쪽 정책과 작업 조건을 통제할 수 있으면 P1은 별도의 관측 비교로 수행할 수 있다.

**시각 자료:** 양쪽 실행 명령·최종 처리율 터미널, 대응하는 Grafana 구간, resident/transfer별 비교 그래프.
실험 전후 고정량의 내부 검산은 허용하지만, 중단했던 고정 작업량 완료시간 캠페인을 재개하는 것은 아니다.

### P2. 이전 FLYT TCP 경로와 제안 SHM 경로의 오버헤드

이 항목이 **새 마지막 단계**다. 한 번에 VM 1개와 GPU 실행 프로세스 1개를 사용하고, 두 구조는 같은 GPU에서 순차 실행한다.
여러 VM의 단독/동시 성능·공정성·간섭은 이번 계획에서 측정하지 않는다. 기존 공유 기능 영상과 I3은 유지한다.

#### P2-0. 비교 대상의 정의와 준비 상태

이전 FLYT 논문은 동일 호스트 배치에서 **데이터 SHM / 제어 TCP**, 원격 배치에서 데이터·제어 TCP를 설명한다.
따라서 “이전 FLYT는 공유 메모리를 사용하지 않는다”라고 표현하면 안 된다.
이 비교의 기본 대상은 **기존 FLYT의 TCP 구성과 제안한 CUDA 요청·응답 및 데이터의 SHM 구성**이다.
여기서 제어 통신은 측정 중 CUDA API 요청·응답이며, 실행 준비 단계의 Cluster Manager 연결과 구분한다.
근거: [FLYT ICPE 2026 논문](https://icpe2026.spec.org/preprint/FLYT_Transparent_and_Elastic_GPU_Provisioning_for_Multi-Tenant_Cloud_Services.pdf),
동일 호스트 전송 설명 및 4.2절·Table 5. 논문 수치는 다른 장비·조건의 결과이므로 우리 측정값과 직접 비율을 계산하지 않는다.

| 비교군 | 실제 경로 | 역할 |
|---|---|---|
| N | 호스트 직접 CUDA 실행 + P1에서 고정한 HAMi 조건 | P1의 참고 기준. 무가상화·무interception 기준이라고 부르지 않음 |
| T | VM → 기존 FLYT CUDA RPC/TCP → RPC 서버 → GPU | 사용자가 요청한 이전 TCP 방식 |
| S | VM → ivshmem/SHM 요청·응답/데이터 → Worker → GPU | 제안 방식 |
| H, 조건부 | VM → 기존 FLYT 제어 TCP + 데이터 SHM → GPU | 원논문의 동일 호스트 SHM 구성 전체보다 개선했다고 주장하려면 필요한 추가 비교군 |

**실행 확정: N/T/S 세 경로를 모든 미세 측정과 처리율에 포함**하며 H는 기본 실행 횟수에 넣지 않는다.
H를 측정하지 않으면 결론도 “기존 FLYT TCP 구성 대비”로 한정한다.
T는 S와 같은 물리 호스트의 VM에서 실행해 물리 네트워크 거리까지 동시에 바꾸지 않는다.
따라서 논문의 원격 배치 성능을 그대로 재현한 시험이라고 부르지 않는다.

저장소에는 [legacy RPC 자료](../../legacy/rpc/README.md), [기준 버전](../../legacy/rpc/versions.lock.yaml),
[기존 구조](../../docs/ARCHITECTURE.md), [RPC HAMi backend 준비 상태](../../legacy/rpc/experiments/hami-backend/README.md)가 남아 있다.
버전 파일의 baseline은 `596a86939bae125d127a9ed6f70d92c332f47644`와 로컬 패치 조합이며,
논문 원본과 동일한 무수정 구현이라고 간주하지 않는다. 실행할 commit·패치 목록·이미지 digest를 별도 동결한다.
특히 legacy HAMi backend 문서는 **구현 후 검증 미실행**으로 기록되어 있어 현재 작동하는 대조군이라고 가정하지 않는다.

준비 단계에서 수행할 작업:

1. 기존 RPC client/server/Manager를 격리된 실험 구성으로 준비하고, 같은 GPU UUID·guest OS·CUDA 버전·공통 probe를 사용할 수 있는지 확인한다.
2. 공통 지원 API로 조회·할당·복사·커널·동기화·해제를 검증한다. 실행 파일 또는 불가피한 링크 차이는 해시로 남긴다.
3. 별도의 짧은 진단 실행에서 **CUDA 호출에 대응하는 TCP socket·RPC 송수신과 실제 데이터 전송 방식**을 확인한다.
   같은 물리 호스트라는 이유만으로 기존 코드의 SHM fast path가 켜진다고 가정하지 않는다.
4. S에서도 request ID·queue 기록·BAR 매핑으로 실제 SHM 경로를 확인한다.
   SSH·Kubernetes·모니터링 TCP 트래픽을 CUDA 전송 트래픽으로 세거나, S의 호스트 전체 TCP 트래픽이 0이어야 한다고 판정하지 않는다.
5. 자동 SM 조정·migration·별도 부하를 비활성화하고, GPU 실행 자원·CPU 배치·정책을 고정한다.
6. 준비가 끝나면 T/S 공통 실행과 검산을 각 1회 통과한 후 본 측정에 진입한다. 이는 예비 실행이며 본 반복에 합산하지 않는다.

**비교 해석:** 원래 FLYT의 MPS와 제안 경로의 HAMi는 다른 자원 제어 계층이다.
주 실험에서 기존 MPS를 유지한다면 전체 SM을 사용할 수 있는 단일 client 조건과 SHM의 연산 제한 비활성 조건을 검증하고,
결과를 **각 구성의 전체 호출·실행 경로 오버헤드**로 보고한다. MPS 100과 HAMi compute 100이 동등하다고 가정하지 않는다.
메모리 설정·실제 여유량도 기록하고, 작은 probe가 두 구성 모두의 한도에 충분히 못 미치도록 한다.

통신 경로의 기여를 더 좁혀 보려면 기존 RPC+HAMi를 먼저 검증해 T/S의 같은 libvgpu·정책·context 조건을 사용하는 보강 비교를 한다.
그 구성은 “자원 제어 조건을 맞춘 FLYT 파생 비교군”으로 표시한다. 동일화가 불가능하면 순수 TCP 대 SHM 지연이라는 인과 주장을 하지 않는다.
동일 backend를 사용해도 직렬화·큐·스레드·polling·동기화 구현 차이가 남으므로 전송 매체만의 효과로 전부 귀속하지 않는다.

#### P2-1. 작은 CUDA 요청의 호출 지연

**목적:** 데이터량이 거의 없는 제어 요청에서 기존 TCP 호출 중계와 SHM 요청 큐의 비용을 비교한다.

| 작업 | 측정 경계 | 확인 사항 |
|---|---|---|
| 장치/상태 조회 1종 | Guest에서 API 호출 직전 → 반환 직후 | 양쪽 모두 실제 원격 실행되는 API 선정. 로컬 cache 응답이면 제외하고 다른 공통 조회 API를 선정 |
| 작은 커널 실행 + 동기화 | launch 직전 → launch 반환, 이어서 sync 완료까지 각각 기록 | launch 반환 지연과 GPU 작업 완료 지연을 구분. preallocated buffer, 같은 PTX·grid·block·입력 |

조회는 실제 원격 전달을 확인한 **`cudaMemGetInfo`**로 고정했다. 완료 API는 세 경로 모두 `cudaDeviceSynchronize`다. legacy `cuCtxSynchronize`의 로컬 fallback은 사용하지 않는다.
작은 커널은 의미 있는 검산 출력을 생성하고, 마지막에 기준 결과와 비교한다. 단순히 성공을 반환하는 stub을 사용하지 않는다.

준비 실행 최소 10초 및 50회 후 **30초 동안 호출을 반복**한다. 반복 횟수 N을 미리 고정하지 않는다.
한 요청이 완료된 뒤 다음 요청을 보내 outstanding 요청을 1개로 맞춘다. 타이밍은 Guest의 같은 단조 시계에서 측정한다.
호출별 표본은 메모리에 기록하고 측정 뒤 저장한다. 파일 출력·화면 렌더링·상세 trace를 측정 루프에 넣지 않는다.
표본이 지나치게 많으면 예비 실행에서 동일한 결정적 sampling 간격을 정하고 T/S에 같이 적용한다.

각 독립 실행의 median/p95/p99, 평균, 호출 수/초를 기록한다. 유효 표본이 적은 p99는 결측 또는 참고값으로 표시한다.
하나의 실행에서 얻은 수천 회 호출을 수천 개의 독립 실험으로 세지 않는다. 독립 반복 수는 구성별 3회다.

#### P2-2. 입력·출력 데이터 전송 비용

**목적:** 메시지 크기에 따라 호출 중계와 데이터 전달 비용이 어떻게 달라지는지 확인한다.

- 크기: **4 KiB / 256 KiB / 4 MiB**, host·device buffer는 측정 전에 할당한다.
- 단위 작업: H2D 복사·완료 확인 → D2H 복사·완료 확인. 각 방향의 완료 지연을 따로 기록한다.
- 각 크기에서 준비 실행 후 30초 반복, N/T/S 각각 독립 3회다.
- Host buffer는 공통으로 지원되는 같은 종류로 고정한다. pageable/pinned 차이와 내부 staging은 명시하며,
  pinned를 어느 한쪽이 대체 구현하면 같은 pinned 조건이라고 보고하지 않는다.
- 같은 패턴의 데이터 왕복을 검산하고 bytes/hash·검사 횟수를 저장한다.
- H2D/D2H 지연과 `payload bytes / 실제 완료시간`의 **유효 전송률**을 계산한다.
  이를 물리 네트워크 대역폭 또는 CPU 복사만의 대역폭이라고 부르지 않는다.
- 작은 메시지의 호출 비용과 큰 메시지의 staging/복사 비용을 나누어 해석한다.

기본 미세 측정은 **조회 1종 + 작은 커널 1종 + 복사 크기 3종 = 5조건**이다.
N/T/S × 5조건 × 3회 = **45개 시간창**이며, 각 시간창은 30초다.
각 구성의 독립 VM/client/server 세션 3개에서 5조건을 순서를 교차해 실행한다.
복사 조건은 한 시간창에 양방향 지연을 따로 저장하므로 6개의 독립 조건으로 중복 집계하지 않는다.
초기 미세 측정 45개와 처리율 18개를 합쳐 기본 63개 구간이다. 실측 변동성 규칙에 따른 확장, 측정 중 화면 미리보기와 겹친 조회 묶음의 제외·새 세션 대체는 최종 결과의 `extension-decision.json`과 `exclusions.json`에 기록한다.
조건 전환 시 queue를 비우고 buffer를 초기화한다. 조건별 동일 VM을 사용한 결과의 상관성도 명시한다.

#### P2-3. 실제 작업에서의 전체 경로 비용

P1의 resident/transfer 60초 측정을 그대로 사용해 **T를 같은 비교 묶음에 추가**한다.
같은 kernel·seed·전송량·동기화·준비 시간·CPU 배치·정책을 사용한다.

| 경로 | Resident | Transfer | 독립 반복 |
|---|---|---|---:|
| N: 호스트 직접 기준 | 60초 | 60초 | 각 3회 |
| T: FLYT TCP | 60초 | 60초 | 각 3회 |
| S: 제안 SHM | 60초 | 60초 | 각 3회 |

P1+P2-3을 함께 준비하면 **총 18회**이고, 기존 P1 12회에 T의 6회가 추가된다.
N/S 결과는 같은 버전·프로그램·조건·캠페인·교차 순서로 수집했을 때만 공유한다.
T 준비 과정에서 S나 기준 조건이 달라졌다면 이전 N/S와 섞지 않고 영향받은 조건을 새로 측정한다.
원래 고정 작업량 완료시간 시험은 재개하지 않는다. 각 측정은 60초 종료 조건으로 수행한다.

#### P2-4. 지표·판정·그림

| 지표 | 계산·해석 |
|---|---|
| T 대비 S의 호출 지연 감소율 | `(L_T - L_S) / L_T × 100`, 같은 API·완료 경계·통계량끼리 비교 |
| 처리율 향상률 | `(Q_S / Q_T - 1) × 100`, 동일 작업 단위·모드 기준 |
| N 기준 처리율 감소율 | `(1 - Q_path / Q_N) × 100`. N의 HAMi 조건과 T의 MPS 차이를 명시 |
| CPU 비용 | guest/QEMU·RPC server 또는 Worker의 CPU core-seconds와 완료 작업당 CPU 시간. guest와 host 중복 합산 금지 |
| 보조 자료 | GPU 이용률, CPU affinity, 요청 수/bytes, queue 또는 RPC 진단 기록 |

**측정 유효성 기준:** 정확성 통과, 의도한 TCP/SHM 경로 확인, 동일 작업과 동기화 의미, 정상 회수,
조건·버전·배치 기록, 각 구성 3개 독립 반복. 실패·준비 오류는 별도 보존한다.
SHM이 빨라야 실험 완료인 것은 아니다. 반복 변동이 크거나 지표별 방향이 다르면 그 범위대로 보고한다.
서로 다른 실행의 median/p95를 단순 빼서 순수 네트워크 비용으로 분해하지 않는다.

**시각 자료**

1. 실제 T/S 실행 명령·버전·GPU UUID·경로 증거를 보여주는 터미널 화면. 경로 진단은 성능 계측과 별도 실행.
2. API별 Guest 관측 지연 median/p95와 반복별 점 그래프. launch 반환과 sync 완료 패널을 구분.
3. 크기별 H2D/D2H 지연·유효 전송률 그래프.
4. N/T/S resident·transfer 처리율 비교와 CPU 비용 표.
5. Grafana는 GPU·CPU의 시간 흐름을 보여주는 보조 화면이다. 이번 실행의 처리율은 30/60초 구간별로 산출하며 1초 처리율 시계열은 수집하지 않았다. 1초 scrape로 마이크로초 API 지연을 직접 측정하지 않는다.

## 10. 공통 시각 자료·원본 수집 규칙

1. 한 실험의 화면에 **run ID, 조건, 실제 명령, GPU UUID, 현재 단계, 결과**가 읽히게 배치한다.
   guest/Worker 터미널과 Grafana를 사용한다. 브라우저 stdout 뷰어라면 그 사실을 표시한다.
2. Grafana는 run/VM/Worker/GPU를 선택하고 절대 UTC 구간을 저장한다. 설정값, 실제 계측값,
   한도선, 할당·OOM·해제·시작·종료 annotation을 구분한다. `Run ID=All` 화면을 조건 비교용으로 사용하지 않는다.
3. GPU/HAMi는 목표 1초 수집, 화면은 5초 갱신으로 시작하되 실제 수집 간격·누락·업데이트 주기를 기록한다.
   앱 live allocated bytes, HAMi 계상, Worker process 메모리, GPU 전체 메모리를 같은 값으로 취급하지 않는다.
4. guest 단조 시계와 host 시각을 실행 중 대응시켜 NTP/UTC step을 검출한다.
   처리율은 단조 시간, 이용률은 대응이 유효한 구간만 사용한다. 예전 long/25처럼 대응 실패한 자료를 숨기지 않는다.
5. 사용자 요청에 따라 신규 기능 시연은 **녹화하지 않는다**. 실제 명령·원본 로그·표준 터미널 또는 Grafana 정적 캡처를 확보한다.
   모든 반복의 원본과 캡처 UTC·실행 식별자를 보존한다. 사후 로그·실측 데이터 조회 화면은 그 사실을 표시한다.
6. 성능 본 측정은 상세 trace를 끄고 동일 collector를 사용한다. 화면 캡처는 관측용 기기 또는 별도 시연에서 한다.
   저장된 본 측정 구간의 Grafana 화면은 “실측 데이터 사후 조회”로 표기한다.
7. 런타임 변경 시 새 버전 묶음으로 분리한다. commit·image digest·probe/라이브러리 hash·정책·CPU 배치를 기록한다.
   과거 구현 검증 결과를 새 버전의 회귀 통과로 자동 승계하지 않는다.
8. `execution`, `correctness`, `measurement_validity`, `enforcement`, `cleanup` 판정을 분리한다.
   기대한 OOM과 예기치 않은 실패를 구분하며, 실패 원본도 보존하고 재실행에 새 ID를 부여한다.

## 12. 실제 진행 순서와 작업량

1. **재사용 자료 배치와 주장 범위 확정:** 다중 GPU 문구를 구현 범위에 맞추고, 기존 그림·영상에 출처/날짜를 붙인다. GPU 실행 없음.
2. **I1+I2 3회:** 필요한 최소 추적 로그·화면 구성 보완 후 요청→호출→검산→회수를 한 흐름으로 확보한다.
3. **I3 3 pair:** 서로 다른 VM 메모리 한도를 동시에 보여주는 핵심 신규 자료를 확보한다. 기존 단독 한도 suite·20회 회수는 반복하지 않는다.
4. **I4-A:** 부하 탐색 최대 3조건, 2×2 정책/경로 진단 4회. 실행 수를 늘리기 전에 진단 결과를 검토한다.
5. **I4-B 조건부 9회:** 제한 계약과 계측이 성립할 때만 진행한다. 기존 long/short 18회 캠페인을 그대로 반복하지 않는다.
6. **P1+P2 준비:** 기존 TCP baseline을 복원·검산하고 실제 전송 경로 및 MPS/HAMi 조건을 확인한다. 비교군 준비·기준 출력 생성은 별도 예비 실행으로 기록한다.
7. **P1+P2-3 총 18회:** N/T/S × resident/transfer × 3회. P1의 N/S 12회를 공유하고 T 6회를 추가하며 같은 캠페인에서 순서를 교차한다.
8. **마지막 비교 P2-1/2:** N/T/S의 조회·작은 커널·3개 복사 크기, 총 45개 30초 시간창. 구조별 독립 세션은 3개이며, 호출별 표본을 독립 반복으로 세지 않는다.

삭제한 A 단독/B 단독/A+B 성능 간섭 실험은 다시 실행하지 않는다. 기존 공유 시연과 I3의 기능·메모리 시험은 유지한다.
고정 작업량, passthrough를 포함한 일괄 3방식 비교, 새 학습 정확성 대규모 반복, 장애 주입,
단일 VM 다중 GPU 실험은 기본 범위에 포함하지 않는다.
특히 다중 GPU를 본문 구현 성과로 유지하려면 단순 실험 추가가 아니라 장치 열거·선택·context·한도·부분 회수 구현부터 별도 계획해야 한다.

최소 목표는 **요청 연결·실제 SHM 호출·동일 GPU 공유·VM별 메모리 한도·정상 회수**를 명확히 보여주는 것이다.
연산 한도는 진단 결과에 따라 구현 성과 또는 남은 한계로 정직하게 제시하고,
성능 분석은 그와 구분해 시간제 처리율과 Guest 관측 호출·복사 지연으로 구성하며,
마지막에는 **기존 FLYT TCP 구성과 제안 SHM 구성의 차이**를 설명한다.
