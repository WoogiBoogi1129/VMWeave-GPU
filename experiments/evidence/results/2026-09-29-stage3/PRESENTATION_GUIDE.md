# 발표 배치안 — 같은 GPU, 다른 한도, OOM 이후 정상 실행

## 슬라이드 1: 같은 요청이 VM별 한도에 따라 다르게 처리되는가?

[동일 요청의 결과 화면](terminal-captures/03-same-request-different-results.png)을 크게 배치한다.

- 왼쪽 A: 한도 **1 GiB**, 요청 **1536 MiB**, `api_result=2`(메모리 할당 오류).
- 오른쪽 B: 한도 **4 GiB**, 요청 **1536 MiB**, `api_result=0`(성공).
- 아래 Worker 응답도 같은 결과이며 `transport_status=0`으로 정상 전달됐다.
- [배치 확인 화면](terminal-captures/01-binding.png)으로 두 Worker의 **동일 물리 GPU UUID**와 서로 다른 VM 연결을 확인할 수 있다.

발표 문장: **“같은 물리 GPU에서 같은 크기의 메모리 요청을 보냈지만, 각 VM에 적용된 한도에 따라 A는 거절되고 B는 성공했습니다.”**

1536 MiB와 실제 로그의 1,610,612,736 bytes는 같은 크기다. 로그의 guest_pointer는 Guest 가상 주소이며 실제 GPU 주소라고 설명하지 않는다.

## 슬라이드 2: 한도 초과 뒤에도 두 VM이 정상 동작하는가?

[후속 할당·B 진행 화면](terminal-captures/04-A-recovery-B-continuation.png)과 [Grafana 진행 화면](grafana-captures/pair-1-progress.png)을 사용한다. 글자가 작아지면 별도 슬라이드로 나눈다.

- A는 VM·프로세스·세션을 재시작하지 않고 **128 MiB 요청에 성공**했다.
- B는 기존 **1536 MiB 할당을 유지**하며 A의 OOM 전후에도 검산 완료 카운터가 증가했다.
- 최종 결과에서 양쪽 불일치 0개와 해제 성공을 확인한다.

발표 문장: **“A의 메모리 한도 초과가 세션 종료로 이어지지 않았고, 작은 재요청은 성공했습니다. 그동안 B도 기존 할당을 유지하며 계산과 검산을 계속했습니다.”**

카운터는 동기화와 표본 검산까지 완료한 횟수다. 1초 대기가 있는 기능 시험이므로 A/B 처리 성능 비교 그래프로 설명하지 않는다.

## 메모리 그래프를 설명할 때

[Grafana 메모리 화면](grafana-captures/pair-1-memory.png)에는 실제 사건 목록과 시각이 함께 있다.

1. 초록: 앱이 성공적으로 할당하고 아직 해제하지 않은 크기.
2. 빨간 점선: VM별 설정 한도.
3. 파랑: HAMi 집계값. 컨텍스트 등으로 앱 할당량보다 클 수 있다.
4. A의 OOM은 성공 할당량을 늘리지 않는다. 실제 오류는 터미널 로그와 사건 annotation으로 확인한다.
5. 아래 GPU 전체 메모리는 두 Worker와 컨텍스트 등을 포함한 별도 관측이다.

각 패널의 세로축 단위를 읽는다. A/B 한도가 다르므로 두 그래프의 선 높이만 비교하지 않는다.

## 표본과 화면의 출처

- 앞 1 MiB의 GPU add 19 결과, 뒤 1 MiB의 보존 데이터를 매회 검사했다. **1.5 GiB 전체의 전수 검사는 아니다.**
- 독립 VM 쌍 3회 모두 원본을 보존했다. 터미널 화면은 pair-1 대표, Grafana는 각 pair별 화면이다.
- 터미널은 **실험 후 원본 로그 조회**, Grafana는 **실측 데이터 사후 조회** 화면이다. 녹화 재생 화면이 아니다.
- 예상 OOM 이후의 동작 확인이며 모든 장애나 악성 접근의 격리를 입증한 결과로 확장하지 않는다.
